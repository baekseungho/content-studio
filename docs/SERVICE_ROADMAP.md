# Mellow Studio 서비스 전환 우선순위

작성 기준: 2026-11-19 (한국 시간)
문서 성격: 제품/개발 계획. 아래 항목은 구현 완료 목록이 아니다.

## 제품 방향과 가정

초기 고객은 체험단·협찬 리뷰와 일상 콘텐츠를 반복 작성하는 개인 크리에이터로 가정한다.
핵심 제공 가치는 사진·실제 경험 메모를 내 말투의 원고로 바꾸고, 업체 미션을 점검하며, 채널별 전달/발행을 돕는 것이다.
운영 형태는 웹 서비스 + Chrome 확장을 우선 제안한다. 모바일에서는 메모/사진/초안 확인을 지원하고, 확장이 필요한 블로그 전달은 지원하는 데스크톱 Chrome에서 수행한다.
현재 작성·미션·줄바꿈·발행 도우미 로직을 활용하면서 계정/저장/작업/연동/과금을 분리한다.

채널별 지원 범위:
- 네이버·티스토리: 초안 작성, 검토, 로그인된 편집기로 전달, 사용자의 최종 발행 확인.
- Instagram·Threads: 사용자 동의를 받은 공식 API 연결 및 발행.
- 확장 배포/상업적 운영 방식은 각 플랫폼과 스토어 정책을 검토하고 지원 범위를 문서화한다. API 종료 공지는 상업적 자동화의 허용 근거가 아니다.

## 현재 구조에서 확인한 전환 과제

- README에서 개인용 로컬 앱으로 설명하며 localhost/Python 실행과 .env 직접 설정을 요구한다.
- 공용 프로세스 토큰은 로컬 요청 보호용이다. 회원 인증과 사용자별 접근 권한을 제공하지 않는다.
- drafts/attempts 등에 소유자 구분이 없다. 사진·내보내기·작업·전달 코드까지 소유자 검사가 필요하다.
- JOBS와 일부 실행 상태는 메모리에 있고 글 생성 잠금은 앱 전체 범위다. 서비스에서는 사용자별 한도와 전체 처리 한도를 구분해야 한다.
- Meta 연결은 운영자의 환경변수에 의존한다. 고객별 OAuth 연결, 암호화 저장, 만료/철회 처리가 필요하다.
- 확장은 개발자 모드의 폴더 로드 방식이다. 폴더 변경으로 1.5.3/1.6.0이 엇갈린 실제 문제가 있었다.
- 임시 사진 터널은 개인용 테스트에 적합한 경로다. 서비스에서는 관리되는 사진 저장·전달·삭제가 필요하다.
- 5,000자 상한과 중복 생성 방지는 이미 있으나 기간별 이용량/크레딧/운영 비용 상한은 별도 과제다.
- 기존 자동 검증과 모의 편집기 테스트는 회귀 검증 자산이다. 실제 고객 환경의 성공률과 글의 사용 가능성은 별도로 측정한다.

## 권장 우선순위

| 순서 | 과제 | 핵심 범위 | 통과 기준 |
| --- | --- | --- | --- |
| 1 | 회원과 데이터 보호 | 로그인/세션, 회원별 자료 소유권, 권한, 사진 비공개, 계정 연결 토큰 암호화, 연결 해제/탈퇴/삭제 | 다른 회원의 원고·사진·작업·내보내기·전달 코드 접근 차단 테스트 통과 |
| 2 | 고객용 연결과 배포 | 실제 도메인/HTTPS, 버튼형 OAuth, Meta 심사 준비, Chrome 스토어 배포 준비, 확장-서버 호환성 및 업데이트 안내 | 개발 지식 없이 가입→계정 연결→첫 원고→전달/발행까지 수행 |
| 3 | 사용량과 원가 통제 | 사용자별 생성 한도, 서비스 전체 예산, 비용 이벤트, 크레딧 예약/확정/복구, 중복 요청 키 | 동시 클릭/응답 유실/실패 복구에서도 중복 차감과 잔액 경합이 발생하지 않음 |
| 4 | 글 품질의 기준과 차별화 | 한국어/영어·업종·말투별 평가 원고, 실제 경험과 검색 정보 분리, 미션 추출/검사, 부분 수정, 사진 분석 재사용 | 미달 조건을 완료로 표시하지 않으며 베타 사용자의 수정량/재사용 의향을 측정 |
| 5 | 전달/발행 신뢰성 | 영구 작업 기록, 재시작 복구, 원고 버전, 결과 불명 상태, 플랫폼별 장애 격리, 편집기 변경 회귀 테스트 | 입력·완료 기록·공개 발행을 구분하며 안전한 복구가 가능 |
| 6 | 운영과 고객 지원 | 운영/테스트 환경 분리, 배포/되돌리기, 백업 복원, 오류/비용 알림, 관리자 화면, 원고 내용을 제외한 지원용 진단 | 운영자가 실패 단계·사용량·영향 범위를 확인하고 백업을 실제로 복원 |
| 7 | 결제와 구독 | 결제 성공 검증, 중복 웹훅 처리, 구독 변경/해지/환불, 이용 조건, 고객 문의 | 결제/구독/크레딧 상태가 일치하고 취소/중복 통지가 검증됨 |
| 8 | 반복 사용 경험 | 내 말투/업체 프로필, 업체 미션 재사용, 마감 알림, 초안 관리, 모바일 메모 | 초대 베타의 반복 사용 데이터를 보고 필요한 항목부터 확대 |

2번의 심사·스토어 준비와 4번의 품질 평가 자료 구성은 1번 개발과 병행한다.
결제는 1~6번의 기본 검증을 마친 뒤 연결한다. 가격은 실제 원가와 베타 사용량을 확인한 뒤 정한다.

## 첫 개발 묶음

첫 묶음은 회원 기반과 사용자별 저장/작업 구조다.

1. 계정/프로필/연결 계정/원고/사진/작업/사용량/전달 시도에 소유자 관계를 설계한다.
2. 모든 API의 인증·권한·오류 형식을 통일하고 단순히 ID를 아는 것만으로 접근할 수 없게 한다.
3. 개인용 데이터를 서비스로 가져오는 절차를 별도 마이그레이션으로 두고 원본 백업과 복구를 검증한다.
4. 작업 기록을 영구 저장하고 사용자별 동시 생성 제한, 전체 처리 제한, 재시작 복구를 나눈다.
5. 실제 도메인에서 확장 연결에 쓰는 짧은 수명의 전달 권한을 회원/원고/플랫폼/목적지와 묶는다.
6. 회원 간 교차 접근·동시 저장·중복 생성·응답 유실 테스트를 배포 차단 조건으로 둔다.

현재 로컬 서버를 그대로 인터넷에 노출하는 방식으로 전환하지 않는다. 회원 권한과 파일 접근 설계가 먼저다.

## 비용/결제 설계 원칙

- 5,000자는 한 원고의 분량 상한이며 월 이용량이나 비용 상한을 대체하지 않는다.
- 사진 분석/검색/최초 생성/말투 다듬기/분량 보완의 실제 공급 비용을 구분해 기록한다.
- 이미지 분석 재사용은 사용자·이미지·모델·처리 버전을 기준으로 하며 다른 회원의 자료를 공유하지 않는다.
- 생성 전 크레딧 예약, 결과 저장 후 확정, 제품 실패 시 정책에 따른 복구를 한 작업 ID로 처리한다.
- 제품 크레딧 복구와 이미 발생한 공급업체 API 비용은 구분한다.
- 결제 통지/생성 완료 통지는 중복되거나 순서가 바뀌어도 동일한 최종 상태가 되게 한다.
- 작성 화면은 간결하게 유지하고 구독/잔여량/결제 내역은 계정 관리에서 확인하게 한다.
- 월 구독 + 포함 작성량을 첫 과금 가설로 검토하고 가격/초과 정책은 원가와 베타 결과로 확정한다.

## 품질 평가와 출시 조건

평가 항목:
- 생성 원고를 실제로 사용할 때의 수정량과 이유.
- 업체 미션 충족/누락 표시의 정확성.
- 사진과 본문 연결, 한국어/영어의 자연스러움, 말투 일관성.
- 선택 장소와 다른 지점의 정보 혼입, 확인하지 않은 경험의 생성 여부.
- 처음 방문한 사용자가 도움 없이 첫 원고를 완성하는 과정.
- 플랫폼/브라우저/확장 버전에 따른 전달 성공·부분 완료·실패 비율.
- 생성 한 건의 공급 비용, 가입 후 반복 사용, 문의 유형과 해결 시간.

제안하는 출시 순서:
1. 비공개 알파: 회원별 자료 보호, 생성/저장/복구, 비용 한도를 확인한다.
2. 초대 베타: 5~10명의 실제 목표 고객으로 설치/연결/글 품질/전달 과정을 검증한다.
3. 소규모 유료: 원가·차감·취소·지원 절차를 검증한 뒤 결제를 연다.
4. 공개 서비스: 배포/업데이트/장애 대응을 운영할 수 있는 상태에서 확대한다.

출시 차단 조건:
- 회원 간 자료 접근, 중복 차감, 확인되지 않은 발행을 성공으로 표시하는 문제가 남아 있음.
- 자료 삭제/계정 연결 해제/백업 복원 절차가 검증되지 않음.
- 실제 고객 계정 대상 권한/심사 및 확장 배포 경로가 준비되지 않음.

전달 성공률 등 수치 목표는 지원 환경과 성공의 정의를 먼저 고정한 뒤 베타 목표로 정한다. 현재 테스트 통과 수를 실제 고객 성공률로 간주하지 않는다.

## 뒤로 미룰 항목

고객과 플랫폼 범위 확대, 영상/릴스 자동 편집, 팀 승인, 대량 예약 발행, 고급 성과 분석은 초기 유료 검증 뒤에 우선순위를 다시 판단한다.
네이버·티스토리 예약 기능을 검토할 때에는 서버 예약 초안 준비와 브라우저에서의 실제 전달/발행을 구분한다. 브라우저 실행·로그인에 의존하는 기능을 서버 단독 예약으로 설명하지 않는다.
